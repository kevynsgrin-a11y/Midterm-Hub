# MidtermWatch navigation and calendar repair

Baseline: `8436b3c99624aa0a8c054a39e89fbb49ab1b7e97` on the repository default branch `claude/civic-calendar-engine-backend-wddfqw`. Work branch: `codex/fix-midterm-navigation-freshness`.

## Behavior

State selectors, cartogram tiles, indexes and breadcrumbs now generate lowercase state paths, matching the static export. The existing Cloudflare proxy redirects legacy uppercase/mixed-case state links to lowercase with HTTP 308 while preserving the query string. Election-detail URLs keep their original uppercase codes. Deploying the frontend and the proxy are separate release steps; Next static export cannot provide this edge redirect by itself.

The homepage lists elections on or after the visitor's local calendar date, sorted by date and state. It refreshes each minute and when the tab becomes visible, includes today, and provides an empty state after the edition ends. The no-JavaScript fallback states the build date explicitly. This filters the existing edition; it does not certify that election sources have been rechecked.

Rebuilding all intake records previously failed once an unmarked published election became more than 30 days old. The frontend exporter may now validate an unchanged, previously verified published record as an archive. Every normalized field must match the prior payload. New or edited stale records still require the existing explicit historical review marker, and all structural validation remains active. Rebuilding unchanged data preserves its original `generated_at`; no election facts or provenance timestamps were edited.

The data runner uses a prepared Python interpreter or the existing uv workflow and never skips validation. `vercel.json` runs `npm ci`, creates a checkout-local `.venv` with Python's standard `venv` module, and installs the existing requirements through that environment's interpreter. The runner prefers this environment over ambient `PYTHON` and system interpreters.

## Deployment evidence and limits

The observed Vercel production alias served July commit `af3f45841d9cb3f52f86356ace82ecef54cd65dc`, while six later deployments failed. Latest failed metadata reports only `npm run build` exit 1 / `BUILD_UTILS_SPAWN_1`. Missing local uv and stale-record validation are independently reproduced local issues, not established causes of those remote failures.

The existing `next.config.ts` headers are ignored by static export and produce a warning. Actual response headers must be supplied by the hosting layer. Existing GitHub Pages automation still uses the separate legacy Python renderer. The repair branch is published in draft PR #12; its hosted install failure is diagnosed below, and no production release is recorded here. The Vercel origin and Cloudflare proxy should be previewed together before promotion. Raw static/Vercel aliases do not gain the proxy redirect automatically.

## Framework security patch

A separate dependency commit pins Next.js to 16.3.3 and updates its required lockfile transitives, following the official August 25 advisory: https://nextjs.org/blog/august-2026-security-release. The static export and unoptimized image configuration reduce the described runtime exposure, but the dependency should still be kept patched.

After this update, all 5 frontend/proxy tests pass and the complete production build passes on Next 16.3.3, including TypeScript and 134 static pages. The data exporter again validates all 74 records without changing `generated/elections.json` or its July 30 generation timestamp. The existing static-export header warning remains as described above.

## Hosted Python install correction

The branch preview at `a0bf17e` failed during installation. The authenticated Vercel build log now establishes that `npm ci` succeeded (94 packages), then system `python3 -m pip` stopped with `externally-managed-environment`: the host's Python installation is managed by uv and protected by PEP 668. This is separate from the earlier unidentified production build failure.

The install command now creates `.venv` and runs its own `python -m pip`; it does not modify the managed interpreter or bypass its protection. Runtime requirements, `pyproject.toml`, `uv.lock`, election data and data-validation rules remain unchanged. No uv CLI availability is assumed. Contributors can still use the existing uv fallback when no prepared interpreter is found.

Regression coverage proves the checkout environment wins over ambient Python on both Linux and Windows, a missing checkout environment can use an explicitly prepared interpreter, incompatible interpreters are rejected, and a real data-validation error stops without fallback. The hosted preview must be rerun to confirm Vercel installation and build success.

Local verification of this correction: all 11 frontend tests and 137 Python tests pass. A fresh isolated Python 3.12.14 environment installs the unchanged runtime requirements and validates all 74 records with the exact original payload hash. The complete Next 16.3.3 build passes TypeScript and exports 134 pages. This validates the installation approach and runner locally, not the hosted image; the existing static-export header warning remains.
